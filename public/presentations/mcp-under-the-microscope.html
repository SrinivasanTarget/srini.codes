The stateless core

The wire, before and after

In plain words: the server now has amnesia. Every request must reintroduce itself.

Before · stateful

clientinitialize: negotiate once
servermints a session ID
serveropen stream, can push requests
infrasticky routing, session store

After · stateless

clientevery request introduces itself
serverany instance answers anything
servercan never push requests
infrasticky routing, session store
Serverless, edge, cacheable, routable. So: where did the state go?
[4:30-6:30] Walk left panel then right. Three security-relevant deletions: no session ID (nothing to hijack), no server push (whole injection channel closed), no resumability (clients re-send; replay problem later). Version rule: header must match body or the request is rejected. End on the question; it's the hinge.

State didn't disappear. It moved.

Tokens, databases, caches. The spec no longer manages them. You do.

What the transport used to hide, the transcript now shows.

Part two

The defender's lens: five ways this breaks in production

[10:45-11:15] Half-time pivot, 30 seconds. Preview: five failure modes, then defenses. Natural speaker seam.
Failure mode 1 · broken state assumptions

The handle is the new session

In plain words: a key card that never expires, and everyone can photocopy it.

"browser_id": "b-abc123"→ transcript→ logs→ pasted chat→ attacker replays it
Hijacking

A handle is just a string: no binding to user, IP, or connection. It lands in transcripts, logs, tickets, chat pastes. Whoever holds it, wins.

Replay

Broken stream? The client sends the request again. No idempotency key in core: twice the payment, twice the deploy.

We deleted session hijacking and reinvented bearer-token leakage, one layer up.
[14:45-16:00] Deepest technical point. Old world: session IDs in headers, invisible to the model, bound to a connection. New world: state rides in model context by design. Sources: Backslash ("state-handle hijacking"), Equixly Aug 2026 (replay/idempotency), Akamai (predictable handles). Image that lands: "a browser_id in a pasted transcript is a live credential."
Failure mode 2 · attacker-controlled continuations

requestState comes back dirty

In plain words: a cookie you bake, hand out, and swallow whole when it returns.

server"I need input" + requestState (my paused memory)
clientanswers … and sends requestState back
servermy "own" state, after two trips across the trust boundary
  • Spec: treat it as attacker-controlled input; sign or encrypt it
  • But expiry and replay bounds are optional homework (SHOULD, not MUST)
Every MRTR server is now a token issuer. Most authors don't know it yet.
[16:00-17:00] Walk the three wire steps. Analogy: 25 years of web cookies say sign it, expire it, bind it, or be owned by it. Guard rails that DO exist: clients must not inspect or reuse it across parallel requests; input_required only on tools/call, resources/read, prompts/get; integrity MUST also covers resource access and business logic, and single-use must be enforced server-side (the SHOULDs alone don't guarantee it). Handoff to Srinivasan after this slide.
Failure mode 3 · capability confusion

Capabilities are claims, not contracts

Shifting claims

Capabilities can change on every request. Caching "what this client supports" is guessing.

Half-support

The rule is revert or reject. Reality: silently half-applied extensions, wrong assumptions.

Downgrade

Force a dual-era server into legacy mode and the old holes reopen.

Smuggling

Gateway reads the headers. Server runs the body. Any mismatch is a policy bypass.

Trust boundaries don't move once. They move on every request.
[17:00-18:00] Emphasize smuggling: the classic HTTP request-smuggling playbook reborn. The spec anticipates it (mandatory header-body validation, HeaderMismatch error -32020 across MCP-Protocol-Version / Mcp-Method / Mcp-Name / Mcp-Param-*); the question is whether every proxy in your chain implements it. New leak surface: x-mcp-header mirrors tool params into Mcp-Param-* headers visible to every intermediary, so never mark secrets mirrorable. Recommendation: refuse legacy fallback for sensitive deployments.
Failure mode 4 · cross-client behavior

Any request, any instance… any tenant?

Isolation

Every request must re-prove whose it is. One missed tenant check can reach every org on the server.

Caches

One tool marks private data cacheScope:"public" and the CDN serves it to everyone.

Guessable IDs

Predictable handles let attackers steer someone else's workflow.

Streams

One notification stream per client: wires can cross between principals.

[18:00-19:00] Anchor on isolation: one tenant-isolation bug in a stateful server exposes every org it hosts. Now every request on every stateless instance is a fresh isolation decision. cacheScope: web cache poisoning is a mature attack field and MCP just opted agents into it. Guessable IDs: Akamai's three cross-tenant scenarios.
Failure mode 5 · authorization mistakes

Stronger spec, same deployment traps

  • The auth server now fetches attacker-suppliable URLs as client identity (CIMD)
  • Token passthrough: banned, still everywhere
  • Scope step-up is now security code you write yourself
  • Confused-deputy consent-skips still work against proxies
  • Prompt injection: no wire protocol fixes it
The spec fixed the OAuth you were supposed to do. Not the OAuth you actually deploy.
[19:00-20:00] Callback to 119/119: that's why this slide exists despite the hardened spec. CVE-2025-6514 is the mirror lesson: OAuth metadata from an untrusted party executed code; now the AS fetches client metadata URLs. Every URL in an auth flow is attacker input. Close part two: "Five failure modes. Now the part you take home."
Live demo · failure modes 1, 4, 5

The Confused Handle: one forged string, three breaches

vulnerable_server.py · :8181 + attack.py
The setup

No sessions. Cross-call state rides in a server-minted handle the client passes back as a plain tool argument, exactly as the spec prescribes. This server trusts it.

Three attacks, one script
  • Guess Bob's handle → read his secret
  • Reuse a read handle on the deploy tool
  • Replay the IDE's handle from a web agent
handle-1007 → Bob is one guess away. A read handle deploys to prod. Alice's IDE handle replays from anywhere.
[DEMO · vulnerable] Runs the real repo (github.com/Thejessree/AGNTConMCPConJapan, talk/demo). Stdlib only, offline, safe on venue wi-fi: ./run_demo.sh vuln. The bug is one line: seq = int(handle.split("-")[1]) trusts data the attacker sent. Attack 1 is stateless IDOR (guessable handle), attack 3 is capability confusion (no per-tool scope), attack 4 is cross-client replay (no audience binding). These map to failure modes 1, 3, 4. On stage: run this, let all three land, then advance to the hardened slide and run the SAME attack.
Live demo · the fix

Same forged string. Denied four ways.

hardened_server.py · :8282 + the same attack.py
What changed
sign → HMAC, server-issued
scope → re-checked per tool
bind → aud = calling client
expire → short TTL
verify → on every single call
Same script, new port
State handles are security tokens. Sign them, scope them, bind them to an audience, expire them, re-verify every call.
[DEMO · hardened] ./run_demo.sh hard (or both for the back-to-back arc, ~4s). The forged/guessed handles now fail as malformed handle; the read handle hits missing scope 'deploy:prod'; the replayed IDE handle hits audience mismatch. Ownership comes from the SIGNED sub, never from a client-supplied id. One diff between the two servers: verify_handle(handle, calling_client, required_scope). This is hardening slides 18-19 made executable. Land it: "we already know how to do bearer tokens; the trap is not noticing you are issuing them."

Hardening 1

Least-privilege tool design

  • Break the trifecta: private data × untrusted input × egress. Remove one leg
  • Separate reader and writer servers, separate scopes, separate approvals
  • Narrow handles: one resource, one verb
  • Tiny scopes first, step up when the task demands it
  • Hash tool manifests; any change means re-review
[20:45-21:30] Each bullet maps to an incident: trifecta to GitHub/Supabase; reader-writer split echoes Microsoft's Azure guidance; manifest pinning answers Invariant's rug-pull PoC and the drift study showing audits decay in weeks. If squeezed, the trifecta bullet is the keeper.

Hardening 2

Treat every handle like a bearer token

handle discipline
bind → to the authenticated user
expire → short TTL, single-use when sensitive
protect → sign or encrypt, reject on failure
scope → one resource, one verb
dedupe → idempotency keys on writes
  • Same recipe for requestState
  • Never trust state just because the model presents it
  • Treat transcripts as secret-bearing
  • Think Shinkansen ticket 🚅: one train, one seat, one departure
If it grants access when presented, it's a credential. Name it one.
[21:30-22:15] Most actionable slide; the left card is the screenshot, let it breathe. One-liner: "we know how to do bearer tokens; the trap is not noticing you're issuing them." Local beat: a Shinkansen ticket is one train, one seat, one departure, useless afterwards; a handle should be that boring. This is the abstract's "explicit state handling," answered.
Hardening 3

Gateway · telemetry · rollout

Gateway

Policy on routing headers, verified against the body. Allowlists, egress control. cacheScope deny-by-default.

Telemetry

Trace context ships in _meta: trace every tool call end to end. Alert on behavior drift.

Rollout

Refuse legacy downgrade where you can. Then red-team the stateless paths: replay, reuse, cross-tenant.

Twelve questions for any stateless MCP system

Auth + audience check on every call?
Handles bound, expiring, signed?
Idempotency keys on writes?
requestState sealed and replay-bounded?

Trifecta: one leg removed?

Downgrade deliberate, or refused?
